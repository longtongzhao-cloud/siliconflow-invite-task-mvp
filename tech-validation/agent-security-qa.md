# 技术验证报告：安全、隐私与 QA

## 1. 结论与验证边界

本报告针对以下 MVP：淘宝订单映射 `N=1/5/10`，客户以硅基流动手机号和短信验证码授权站点代为取得邀请码；抢单人先完成本站手机号登录并登记支付宝收款信息，再领取 30 分钟名额；15 分钟站内提醒；系统查询注册、邀请码归属及首次有效实名认证状态；订单 24 小时有效；最终最多锁定 `N` 个奖励，每人 5 元，首版人工打赏。

当前安全结论是 **有条件可验证，不可直接判定可上线**。无官方开放 API 或书面授权时，第三方登录和状态查询能力可能依赖未公开接口、网页会话或页面结构。技术上短期可用并不能证明调用获准、长期稳定或数据语义可靠。技术验证必须遵守以下边界：

- 不绕过滑块、验证码、频率限制、风控或访问控制；不批量试号。
- 手机号持有人必须在本网站清楚知情并主动输入其一次性验证码；工作人员不得向用户索取验证码，也不得在聊天中代收。
- 实名认证只能由真实用户在硅基流动官方页面自行完成；本站不采集姓名、身份证号、证件照片、人脸数据。
- 如果获得邀请码或状态必须规避平台控制、伪造客户端、滥用泄漏密钥或长期持有超出用户授权范围的令牌，则该技术路径直接 `NO-GO`。
- 技术验证只使用经同意的专用测试账号和最少数量的新用户，不触发真实打赏；支付只验证内部待支付账本和人工操作流程。
- 上线前须单独完成硅基流动条款/授权审查、隐私告知与同意文本审查；这两项不是代码测试可以替代的。

## 2. 资产、参与者与信任边界

### 2.1 重点资产

| 资产 | 敏感度 | 主要后果 |
|---|---:|---|
| 硅基短信验证码 | 极高、瞬时凭证 | 账号接管、越权登录 |
| 硅基会话令牌/Cookie | 极高 | 24 小时内代用户访问账号 |
| 本站手机号登录会话 | 高 | 冒领任务、篡改收款信息 |
| 手机号、支付宝账号和收款人姓名 | 高、个人信息 | 诈骗、撞库、定向骚扰、错误付款 |
| 邀请码、硅基用户 ID、注册/认证状态 | 中高 | 邀请关系泄露、错误判奖 |
| 淘宝订单号、SKU、签名链接 | 中高 | 越权激活、订单劫持 |
| 名额、验证结果、奖励账本、支付流水号 | 高、资金数据 | 超发、少发、重复支付、审计失真 |
| 加密主密钥、短信和管理后台凭据 | 极高 | 全库解密或批量滥用 |

### 2.2 威胁参与者

- 外部攻击者：撞库、短信轰炸、钓鱼、盗取订单链接、XSS/CSRF、接口枚举。
- 恶意客户：提交他人手机号、复用订单、套取登录状态、伪造 SKU/人数。
- 恶意抢单人：多账号/多设备抢占、重复实名、伪造完成状态、替换支付宝收款人。
- 内部管理员：无业务需要查看手机号、支付宝信息或解密硅基会话，擅自标记已支付。
- 上游变化：硅基接口、字段语义、会话寿命或风控变更，导致状态误判；淘宝订单权限变化。
- 系统故障：定时任务延迟、并发事务冲突、重复消息、时钟漂移和重试导致超发。

### 2.3 信任边界

浏览器、本站边缘层/反向代理、应用服务、数据库、密钥服务、后台管理端、硅基流动、短信服务、淘宝与人工支付宝操作均为独立边界。任何来自浏览器、淘宝参数或硅基响应的数据都须在服务端重新校验；前端倒计时和页面显示不具备结算效力。

## 4. 令牌与验证码安全设计

### 4.1 硅基会话令牌

建议采用应用层信封加密：

1. 每条会话生成独立数据密钥或由受控密钥派生，使用具备认证能力的算法（如 AES-256-GCM）。
2. 每次加密使用不可复用的随机 nonce；把 `provider=siliconflow`、本站用户 ID、订单 ID、记录 ID、到期时间和密钥版本作为 AAD，防止密文被跨用户或跨订单替换。
3. 主密钥不与数据库、代码或 `.env` 备份放在一起；生产环境使用云 KMS/密钥托管服务。服务进程只获解密所需的最小权限。
4. 数据库字段仅包含 `ciphertext`、`nonce`、`key_version`、`expires_at`、用途和不可逆令牌指纹；任何 API、后台、日志均不返回明文。
5. 仅执行邀请码读取和订单状态核对的专用服务可解密。每次解密记录操作者/服务身份、记录 ID、目的、时间和结果，但不记录令牌。
6. `expires_at <= created_at + 24h` 是数据库约束。到期后先使应用拒绝解密，再由高频清理任务擦除密文；服务启动时补跑清理。备份中的密文依靠数据密钥销毁实现不可恢复。
7. 用户撤回授权、订单结束、上游返回未授权或异常账号状态时立即失效并清除，不等待 24 小时。
8. 密钥轮换须支持旧版本受控解密和重新加密；出现泄露时可按版本吊销。开发、测试、生产密钥严格隔离。

禁止做法：把令牌放入 URL、浏览器 Cookie/LocalStorage、客户端埋点、错误信息、截图、客服聊天、数据库调试字段或通用缓存；用固定 IV/nonce；在代码仓库保存密钥；管理员提供“一键查看令牌”。

### 4.2 短信验证码

- 验证码从 TLS 页面直接提交到本站敏感端点，仅在当前进程完成一次上游交换，随后丢弃；不得写数据库、缓存、异步队列或重试载荷。
- 验证码字段使用固定键名并在应用、网关、WAF、APM、错误追踪和审计 SDK 的最前端统一剔除。仅靠正则替换日志文本不够。
- 敏感路由禁止请求/响应 body 捕获、浏览器会话回放、热图和第三方分析脚本；错误只记录随机 `request_id` 和错误类别。
- 页面禁止验证码进入 URL/query、浏览器历史或自动保存；响应设置 `Cache-Control: no-store`、合理 CSP 和 `Referrer-Policy: no-referrer`。
- 不把短信发送号码 `10686303119360` 作为鉴真或路由依据；发送号码可能变化或被伪装。页面只提示用户核对用途和域名，不诱导用户向客服转发验证码。
- 上游交换失败时要求用户重新提交新验证码；不把原验证码放入通用重试队列。

测试注意：托管语言无法可靠保证瞬时内存“物理清零”，因此验收目标应是“不持久化、不传播、最短生命周期”，不能宣称绝对零残留。

角色建议至少拆分为客服、审核、支付、审计和系统运维。客服不应看到完整支付宝信息，支付人员不应解密硅基令牌，运维不应直接改奖励状态。生产管理员强制 MFA，所有提权、解密、修改收款信息、标记支付和导出操作进入不可变审计日志。

## 6. 名额、超时、补做和支付的不变量

### 6.1 状态定义

抢单记录建议使用不可跳跃的服务端状态机：

`ACTIVE`（30 分钟保护中） -> `VERIFIED_LOCKED`（已验证且锁定奖励） -> `PAYOUT_PENDING` -> `PAID`

`ACTIVE` -> `EXPIRED`；`EXPIRED` 在订单 24 小时内可因补做成功尝试原子转为 `VERIFIED_LOCKED`，但只有剩余容量在保护所有当前有效抢单后仍大于 0 才成功，否则转为 `VERIFIED_NO_REWARD`。订单过期则转为 `ORDER_EXPIRED`。

`PAYOUT_PENDING` 支付失败应进入 `PAYOUT_RETRY/REVIEW`，仍计入已锁定奖励，不能释放名额。不得因为人工支付暂未完成而让其他人占用同一奖励预算。

### 6.2 核心计数

- `active_reservations`：当前 `ACTIVE` 且 `reservation_expires_at > db_now()` 的人数。
- `reward_locked`：`VERIFIED_LOCKED/PAYOUT_PENDING/PAYOUT_RETRY/PAID` 的去重人数。
- 永久硬不变量：`0 <= reward_locked <= N` 且 `reward_locked + active_reservations <= N`。
- 抢单：只有事务内重算满足 `reward_locked + active_reservations < N` 才可新增 `ACTIVE`。
- 活跃者完成：同一事务把其从 `ACTIVE` 移出并加入 `reward_locked`，总和不变。
- 超时者补做：只有事务内满足 `reward_locked + active_reservations < N` 才能加入 `reward_locked`，否则只记录完成但无奖励。
- 订单成功条件：`reward_locked == N`；人工付款未完成时不可把“已锁定”显示成“已打赏”。

所有计数以数据库为真源，不能信任前端缓存或独立 Redis 计数。对订单行执行 `SELECT ... FOR UPDATE`，或使用具备同等语义的原子条件更新；锁顺序固定为 `order -> assignment -> reward` 防止死锁。过期扫描、上游轮询、用户刷新和人工审核都必须走同一状态转换服务。

### 6.3 时间语义

- 所有判定使用数据库 UTC 时间；前端倒计时仅展示。
- 明确定义边界：建议 `observed_at < reservation_expires_at` 视为保护期内，等于截止时刻视为超时。
- 在没有上游可信实名认证时间戳时，只能用本站“首次成功观察到有效认证”的服务端时间，不能用用户点击“我已完成”的时间。轮询间隔会导致误差，必须在技术验证中测量并向业务说明。
- 15 分钟提醒以消息幂等键 `assignment_id:reminder_15m` 保证最多一次；延迟到超时后才执行的提醒应丢弃。
- 订单有效截止时间优先于名额截止；订单 24 小时到期后不得再锁定奖励。

### 6.4 唯一约束与幂等键

- 淘宝订单激活：`UNIQUE(taobao_order_id)`；SKU 到 `N` 的映射只能来自服务端受信订单数据。
- 同一任务抢单：`UNIQUE(order_id, site_user_id)`，禁止靠刷新重复领取。
- 有效邀请资格：对规范化的硅基用户标识建立全局唯一奖励约束；若上游没有稳定 ID，此要求无法可靠实现。
- 奖励：`UNIQUE(assignment_id)`；支付意图幂等键使用不可变 `reward_id`。
- 人工支付流水号：标准化后全局唯一；“标记已支付”要求再次输入或扫描流水号、展示收款人末位并二次确认。
- 状态查询事件使用上游用户 ID、状态版本/观察时间生成幂等键，重复轮询不得重复创建 reward。

## 7. 风控限制

### 7.1 短信与登录

- 发送验证码建议起始阈值：同手机号 60 秒 1 次、1 小时 5 次、24 小时 10 次；同 IP/设备设置更高但有限的聚合阈值。具体数值在压测和真实误伤数据后调整。
- 连续错误验证码或异常滑块结果触发递增冷却；响应统一为“请求已受理/暂不可用”，不暴露手机号是否注册、订单是否存在或上游详细错误。
- 订单客户登录链路须先验证一次性订单令牌；抢单人登录链路与客户链路分离。异常突增自动暂停上游短信调用并告警。
- 不自建绕过滑块的识别服务，不转售或共享上游会话。

### 7.2 重复与欺诈

- 本站手机号、硅基稳定用户 ID、支付宝账号 HMAC、淘宝订单 ID 分层去重；每一种信号都明确其证明范围。
- 手工登记支付宝账号不能证明账号归属、自然人身份或与硅基实名主体一致。第一版只能降低重复概率，不能承诺“同一支付宝/身份证/自然人绝对只能一次”。
- 微信未完成官方 OAuth 时也不能把手机号或昵称当稳定身份。设备信号容易变化且可能多人共享，只参与风险评分。
- 硅基返回的“首次有效认证”如经样本验证能可靠排除重复实名，应作为主要资格证据；如果该字段不存在、语义漂移或不同端不一致，则自动判奖必须关闭。
- 高风险行为进入人工复核：短时间多账号同 IP/设备、多个账号共用收款信息、注册/认证时间异常、上游状态反复、客户和抢单人关系异常。

### 7.3 Web 与后台

- 全站 HTTPS/HSTS；本站登录 Cookie 使用 `Secure`、`HttpOnly`、合适 `SameSite`，登录后轮换会话 ID。
- 严格 CSP，敏感页面禁止第三方 JS、广告和聊天挂件；输入输出做上下文编码，数据库查询参数化。
- 所有状态改变接口做 CSRF 防护和对象级授权；订单号、用户 ID 不能作为授权依据。
- 管理端独立域名或网络边界、MFA、短会话、设备/地理异常告警；生产环境禁止通用数据库管理页面暴露公网。
- 密钥、令牌和个人信息禁止进入工单、群聊和截图；客服排障只使用 request ID 和遮罩字段。

## 8. 验收测试清单

以下用例均须保留测试编号、环境、构建版本、服务端时间、期望/实际结果和脱敏证据。P0 用例全部通过才可进入有限内测。

### A. OTP 与令牌

- **SEC-OTP-01**：提交标记用测试验证码后，扫描应用日志、反向代理日志、APM、错误追踪、审计日志、队列、缓存、数据库和浏览器网络历史；任何位置不得出现明文验证码。
- **SEC-OTP-02**：制造上游 4xx、5xx、超时和应用异常，确认错误栈与重试载荷无手机号全值、验证码、令牌和上游完整响应。
- **SEC-OTP-03**：重复提交同一验证码、并发提交、过期提交，均不得产生多份会话或重复订单绑定。
- **SEC-OTP-04**：未持有效订单令牌发短信、枚举手机号、超限发送，确认统一响应、限速和告警生效。
- **SEC-TOK-01**：直接读取数据库和备份，只能看到认证密文；篡改任一密文字节、nonce、AAD 中的用户/订单/到期时间后必须解密失败。
- **SEC-TOK-02**：不同用户、订单间交换密文，必须失败；低权限服务和所有后台角色均不能解密。
- **SEC-TOK-03**：订单完成、用户撤回、上游未授权、24 小时到期四种情形均立即拒绝使用；清理任务和服务重启补偿均清除密文。
- **SEC-TOK-04**：检查浏览器存储、Cookie、URL、Referer、页面源代码和接口响应，确认无硅基令牌。
- **SEC-TOK-05**：演练密钥版本轮换和单版本吊销，确认新写入用新版本、审计完整、旧密钥撤销后相应会话不可用。

### B. 上游状态语义

- **QA-UP-01**：经本人同意的已注册邀请人账号，人工比对官方页面与本站取得的 8 位邀请码；必须完全一致，完整链接只作备用。
- **QA-UP-02**：用真实的新用户样本记录注册前、已注册未认证、首次有效认证后的原始字段和本站判定；三阶段不得错序。
- **QA-UP-03**：使用合规可获得的重复/无效认证样本，验证系统不会锁定奖励；若无法取得该样本，则该项标记未验证，不能宣称已具备身份证维度去重。
- **QA-UP-04**：上游登出、令牌过期、密码/安全状态变化、接口 401/403/429/5xx 时，系统进入待重试或人工审核，不得把未知当成功或失败。
- **QA-UP-05**：记录状态轮询延迟、首次观察时间与官方页面变化时间差；在峰值和正常网络下给出 P50/P95/P99，作为 30 分钟边界误差依据。
- **QA-UP-06**：改变或缺失关键字段、返回未知枚举值，必须触发 schema 告警并停止自动判奖，不能使用宽松 truthy 判断。

### C. 名额与并发

- **QA-SLOT-01**：`N=1` 时 50 个并发抢单请求，必须恰好 1 个 `ACTIVE`，其余明确返回名额已满。
- **QA-SLOT-02**：分别对 `N=5/10` 做并发抢单，任一时刻 `reward_locked + active_reservations` 不得超过 N。
- **QA-SLOT-03**：同一用户双击、刷新、网络重放和客户端重试，只能得到同一 assignment。
- **QA-SLOT-04**：完成事件与 30 分钟过期任务同毫秒竞争，结果遵循统一数据库时间边界，且总计数不变或减少，绝不增加两次。
- **QA-SLOT-05**：已超时者补做与新用户抢最后一个空位并发 100 次，每次仅一方成功；若新用户已经处于有效保护期，补做者不得抢走该保护名额。
- **QA-SLOT-06**：`reward_locked=3, active=2, N=5` 时补做者只能得到无奖励完成；`reward_locked=3, active=1, N=5` 时最多一个补做者可锁定奖励。
- **QA-SLOT-07**：24 小时订单截止与补做成功竞争，截止后不得锁定；人工改浏览器时间无效。
- **QA-SLOT-08**：过期扫描重复执行、延迟执行、并行执行和服务重启补跑，不重复释放、不产生负计数。
- **QA-SLOT-09**：15 分钟提醒任务重复投递最多产生一次站内消息；已完成、已超时或订单关闭后不再发送。
- **QA-SLOT-10**：数据库死锁/事务回滚、缓存失效和消息重复后，以数据库重算仍满足两条硬不变量。

### D. 奖励与人工支付

- **QA-PAY-01**：同一完成事件重复轮询 100 次，只生成一个 reward 和一个待支付项。
- **QA-PAY-02**：两个管理员同时标记同一 reward 已支付，只允许一个成功；重复流水号不能用于其他 reward。
- **QA-PAY-03**：修改支付宝收款信息后，已有支付确认失效并重新复核；历史值保留加密审计但普通客服不可见。
- **QA-PAY-04**：人工标记失败/撤销不得释放资格；进入异常处理账本，确保不让第 `N+1` 人获得奖励。
- **QA-PAY-05**：页面分别显示“完成待支付”“支付处理中/待人工”“已打赏”，不得把锁定名额等同到账。
- **QA-PAY-06**：对账导出默认遮罩手机号和支付宝账号；只有支付角色按单查看完整信息且产生审计事件。

### E. 权限、隐私与恢复

- **SEC-AUTH-01**：客户 A、抢单人 B、客服、支付、运维分别尝试访问他人订单、邀请码、收款信息、令牌和奖励，验证对象级授权矩阵。
- **SEC-AUTH-02**：对订单链接、用户 ID、assignment ID 做枚举，响应不得泄露对象存在性或敏感状态。
- **SEC-WEB-01**：覆盖 XSS、CSRF、SQL 注入、开放重定向、SSRF、文件导出公式注入和敏感缓存测试。
- **SEC-ADMIN-01**：管理员无 MFA、会话过期、权限撤销后访问、批量导出和越权解密均被拒绝并告警。
- **PRIV-01**：验证隐私告知包含处理目的、字段、第三方、24 小时会话期限、收款信息用途、撤回/删除渠道和自动判定规则；同意前不得请求硅基验证码。
- **PRIV-02**：执行用户撤回、账号注销、订单结束和期限到达的删除流程，确认主库、缓存、搜索索引、日志和加密备份处置一致。
- **OPS-01**：模拟上游不可用、限流、字段漂移、数据库故障和定时任务中断；系统须暂停新抢单或转人工，不得错误结算。
- **OPS-02**：恢复备份到隔离环境，确认已销毁数据密钥的过期会话不可解密，恢复环境无短信/支付外联能力。

## 9. 必须由人工配合的验证步骤

1. **业务所有者/合规人员**：确认硅基流动条款是否允许用户授权第三方代理登录、保存会话和读取邀请/认证状态；取得书面许可最佳。没有明确依据时，结论必须写为高残余风险，不能包装成官方接入。
2. **邀请人测试账号持有人**：使用专用账号，在本站页面本人接收并输入 OTP；验证码不通过微信、淘宝聊天、截图或测试文档传递。登录后本人在官方页面核对邀请码。
3. **真实新用户测试者**：至少覆盖“注册未认证”和“首次有效认证”。测试者自行在硅基官方页面完成实名，并提前签署/确认测试知情同意；团队不接触其身份证、人脸和支付宝认证过程。
4. **重复/无效认证样本提供者**：只有在平台规则允许且无需伪造身份时才验证。无法合法获得样本就明确标记未验证，不能创建假身份补齐测试。
5. **安全测试人员**：使用专门的标记 OTP/令牌在非生产环境检查全链路泄露；访问生产密钥和真实令牌不是验收必要条件。
6. **管理员/财务角色**：用虚拟 reward 和虚构/脱敏收款信息演练领取、复核、标记支付、撤销和对账。技术验证阶段不进行真实 5 元转账。
7. **系统负责人**：验证 24 小时清理、用户撤回和密钥吊销，签字确认数据库、缓存、队列、APM 与备份范围均已覆盖。
8. **业务验收人员**：人工对照官方邀请记录与本站状态，确认“已注册数、已认证数、有效认证数、任务状态”的定义分别是什么，避免把展示字段误当结算字段。

每个真人测试者必须使用自己的账号和身份，不共享登录凭据，不代替他人实名。任何页面截图先遮罩手机号、用户 ID、邀请码、订单号和收款信息后才可进入报告。

## 10. 可观测性与告警

允许记录的事件：随机 request ID、内部用户/订单 ID、动作类型、状态转换前后、服务端时间、上游响应类别、延迟、重试次数、密钥版本和操作者角色。禁止记录 OTP、硅基令牌、完整手机号/支付宝账号、完整上游响应体和敏感请求体。

最低告警项：

- OTP 发送量、失败率或单 IP/设备聚集异常；上游 401/403/429/5xx 激增。
- 解密次数异常、非预期服务尝试解密、过期令牌仍被访问。
- 任何订单出现 `reward_locked + active_reservations > N` 或负计数；立即冻结该订单支付。
- 同一硅基用户 ID/支付宝 HMAC 多次获奖、同一流水号复用、管理员批量查看收款信息。
- 上游字段 schema/枚举变化、认证状态回退、P95 状态观察延迟超过阈值。
- 到期清理积压、备份/日志脱敏扫描命中敏感模式。

## 11. Go / No-Go 门槛

### 可进入有限内测的必要条件

- 所有 P0 测试通过，尤其是 OTP 全链路无持久化、令牌加密/删除、并发不超 N、奖励/支付幂等。
- 三阶段状态样本证明邀请码、注册、首次有效认证语义稳定；关键字段变化会自动关闭判奖。
- 用户授权和隐私告知已审查；真人测试和官方页面操作均有明确同意。
- 管理后台 MFA/RBAC/审计有效；人工支付流程可区分待支付与已支付。
- 已测量状态轮询延迟并确定 30 分钟边界的产品规则和申诉路径。
- 硅基调用方式不需要绕过技术控制，且业务所有者书面接受无官方 API 带来的条款与稳定性残余风险。

### 必须停止的条件

- 验证码、令牌或完整个人信息出现在任一持久化日志、分析平台、队列或前端存储。
- 令牌不能在 24 小时、撤回或订单结束时可靠失效/清除。
- 无法稳定区分首次有效认证与重复/无效认证，或没有稳定硅基用户标识用于资格幂等。
- 任一并发测试产生第 `N+1` 个锁定奖励或重复支付记录。
- 必须规避验证码/滑块/风控、伪造设备或使用非本人身份才能完成流程。
- 上游条款或平台通知明确禁止该代理登录、令牌保存或数据读取方式。

## 12. 残余风险

即使上述测试全部通过，仍无法消除以下风险：未公开接口随时变化或封禁；上游字段并非正式合同语义；人工登记支付宝信息无法确认账户所有权；手机号、设备、微信和支付宝信号不能在不接官方身份接口的前提下证明同一自然人；状态轮询时间不等于官方认证事件时间；个人开发者/个人店铺是否具备开展该业务和处理资金、个人信息的资格属于法律与平台规则问题。

因此技术验证的正确产物应是“经授权测试样本下的可重复证据、失败模式和停止开关”，而不是对生产可持续性或合规性的保证。
