# 技术验证总报告

验证日期：2026-08-14  
目标：验证“淘宝订单 -> 客户授权取得 SiliconFlow 邀请码 -> N 人抢单 -> 注册与首次有效认证 -> 人工打赏”的关键技术可行性。

## 结论

当前结论分为两层：

- **任务平台自身可做**：淘宝 SKU 映射、任务链接、N 人名额、30 分钟保护、24 小时截止、站内提醒和人工支付宝打赏均有可落地设计；名额、并发和会话安全模型已通过本地测试。
- **上游自动化当前为 `NO-GO`**：官方网页登录端点是同域内部接口，不是开放给第三方的 OAuth/API；当前公开协议和隐私提示不支持第三方收集 SiliconFlow 验证码、代理登录、保存会话并自动读取邀请记录。用户已明确没有合作授权，因此不能把私有网页接口联调作为下一步执行项。

已证明参考站确实使用代理登录与后台聚合实现目标人数、注册人数和认证人数，并非让客户反复打开“我的邀请记录”。任务名额、超时补做和 24 小时会话加密模型也已通过本地可执行测试。

尚未证明的是：不依赖参考站私有后端时，自建服务能否通过**获准的第三方接口**稳定取得 8 位邀请码、邀请归属、用户 ID 和“首次有效认证”字段。目前没有发现该类开放接口。本次未发送短信、未提交验证码、未登录、未注册、未实名、未付款。

## 已复现的参考站架构

```text
客户订单链接
  -> 手机号 + 人工滑块 + SiliconFlow 短信验证码
  -> 参考站后端代理登录
  -> 返回邀请码
  -> 确认绑定订单

抢单人邀请码路径
  -> 手机号 + 人工滑块 + SiliconFlow 短信验证码
  -> 注册/登录后获得会话
  -> 资料代理读取 user ID + authInfo
  -> 参考站后台聚合注册数与认证数
  -> 匿名任务配置展示 needNum/regNum/authNum
```

参考站公开前端使用的认证字段包括 `isAuth`、`authTime`、`isSystem`、`isFirstAuth` 和 `authStatus`。这足以说明其展示层能区分认证类型，但不能证明这些字段在所有账号状态下具有稳定的结算语义。

独立检查官方客户端还确认：手机验证码接口前置网易易盾滑块，登录时另带设备环境 token；仅复刻手机号和验证码两个字段不能稳定工作。官方短链可把邀请码带入官方登录页，但官方公开 API Reference 未列出推荐官、邀请记录或实名认证状态接口。官方隐私提示要求不要在非 `siliconflow.cn` 域名登录或向他人提供短信验证码，这与原设想的本站收码流程直接冲突。

参考站还存在不应复制的问题：任务配置可匿名读取完整邀请人手机号和邀请码；抢单人会话被写入浏览器存储。自建系统应使用不可枚举任务令牌、手机号脱敏、对象级授权，并让上游会话只在服务端以密文保存。

## 已确认的产品硬需求：代理登录与会话保存

产品负责人确认第一版仍要求本站后端代理登录 SiliconFlow，并保存登录后取得的会话令牌。该要求的技术实现基线为：

- OTP 仅在一次代理登录请求的内存中使用，不写数据库、缓存、队列、日志、APM 或错误追踪；
- 会话令牌只保存在服务端，不返回浏览器，不写 `localStorage`、前端 Cookie 或 URL；
- 采用 AES-256-GCM 信封加密，AAD 绑定本站用户、订单、上游平台、到期时间和密钥版本，生产主密钥置于独立 KMS；
- 会话有效期取 SiliconFlow 实际有效期与本站 24 小时上限的较小值；用户撤回、订单结束、上游登出或到期时立即销毁；
- 每次读取邀请码或邀请记录前重新检查授权状态、订单状态和过期时间；上游返回 401/403、字段漂移或风控挑战时停止自动判定并转人工；
- 禁止多人共享同一上游会话，禁止把会话令牌提供给客服、抢单人或客户下载。

本报告将该链路标记为“技术可实现、非官方开放接入、经营者风险接受”，而不是“SiliconFlow 已授权”。当前只完成合成令牌加密与生命周期验证；未对真实账号发送短信、提交 OTP 或保存真实会话。

## 本地测试结果

### 任务规则

5/5 通过：

- 单名额保护；
- 30分钟超时释放；
- 订单未满时允许超时补做；
- 24小时订单截止；
- 重复完成幂等。

### 并发竞争

6/6 通过：

- `N=1`，100个并发请求仅1个成功；
- `N=5`，100个并发请求仅5个成功；
- `N=10`，100个并发请求仅10个成功；
- 同一用户50次并发重试仅生成1个名额；
- 超时补做与新抢单竞争最后一个位置，200轮每轮恰好一个胜者；
- 新抢单处于30分钟保护期时，超时补做不能抢走其位置。

生产实现必须保持硬不变量：

```text
reward_locked + active_reservations <= N
```

其中人工支付失败仍属于 `reward_locked`，不能重新释放。

### 会话安全

8/8 通过，使用的均为合成令牌：

- AES-256-GCM 密文不包含明文；
- 合法上下文可解密；
- 跨订单、跨用户密文交换失败；
- 任一密文字节篡改失败；
- 到期拒绝解密；
- 超过24小时TTL拒绝创建；
- 撤回后拒绝解密。

生产密钥必须存放于独立 KMS 或同等密钥托管系统，不能和数据库、代码或备份放在一起。OTP 只在单次请求内存中使用，不得进入数据库、缓存、队列、APM、错误追踪或前端存储。

## 淘宝侧决策

标准映射应使用稳定的 `outer_sku_id`：

```text
SF_INVITE_1  -> 1人
SF_INVITE_5  -> 5人
SF_INVITE_10 -> 10人
N = sum(SKU人数 * 子订单购买数量)
```

订单付款消息和交易详情均需要权限与店铺授权。必须在你的淘宝开放平台控制台核对：

- 当前应用类型与主体；
- 是否有 `taobao.trade.fullinfo.get`；
- 是否能订阅付款、关闭和退款消息；
- 店铺主账号能否给应用授权；
- 是否有购后卡片、服务登记或机器人权限；
- 当前商品类目是否允许所设计的站外步骤。

在聊天专项权限未获批准前，MVP 使用淘宝官方服务登记/购后卡片作为入口，邀请码在订单网页直接展示，客服人工一键复制回聊。

## 经营与隐私边界

- 在同一经营者全部平台和网店年交易额合计不超过10万元、且该业务本身不属于依法须取得行政许可的活动时，可以按零星小额交易免于市场主体登记。对应公示语应是“个人从事零星小额交易活动，依法不需要办理市场主体登记”，不是“个人利用自己的技能从事便民劳务”。
- 免于市场主体登记不免除税务、隐私、消费者保护义务，也不自动取得淘宝、支付宝或 SiliconFlow 的接口权限；超过10万元后应及时办理登记。
- 该模式存在被认定为任务撮合或职业中介的可能性，正式经营前应向实际经营地市场监管与人社部门书面咨询。
- 第一版只能称“登记支付宝收款信息”，不能称“支付宝实名绑定”；人工核对不能证明其与 SiliconFlow 实名主体一致。
- 不采集身份证号、证件照片或人脸数据。硅基用户ID可做奖励幂等，但应加密或HMAC化。

## 下一道验证门

第一道门不是验证码测试，而是取得 SiliconFlow 对以下行为的书面确认：第三方代收用户 OTP、代理登录、服务端保存会话最多24小时、读取邀请码/邀请记录/认证状态，以及用于外部有偿任务结算。

询问内容已整理为 `siliconflow-authorization-request.md`。必须取得明确的书面许可和稳定接口说明，不能把用户在本站勾选同意视为 SiliconFlow 对内部接口的授权。

这里需要区分两个法律与技术对象：

- **用户对本站的授权**：勾选可以证明用户同意本站在告知范围内处理其手机号、验证码和会话，并委托本站代为操作；这是隐私与委托层面的依据。
- **SiliconFlow 对本站的授权**：决定本站能否调用其内部接口、保存平台会话和自动读取数据；只能来自 SiliconFlow 的协议、开放接口规则或书面许可。

前一项不能替代后一项。若产品负责人仍决定在只有用户勾选、没有上游授权时上线，应记录为经营者主动接受的合同、封号、接口中断和数据争议风险，不能在技术报告、用户页面或对外宣传中表述为“SiliconFlow 已授权”。

只有得到书面许可或正式第三方接口文档后，才按照 `live-test-runbook.md` 执行一次受监督测试：

1. 邀请人本人登录并在官方页面核对取得的8位邀请码。
2. 一名从未注册的新用户通过该邀请码注册，取得稳定用户ID并证明归属正确。
3. 记录未认证到首次有效认证的字段变化及观察延迟。
4. 如能合法取得重复/无效认证样本，验证不会锁定奖励；无法取得则不得宣称支持身份证维度去重。
5. 验证OTP没有进入任何持久化系统，会话在撤回、订单结束或24小时到期时不可用。
6. 全程不绕过滑块、验证码、风控或官方实名步骤。

未取得书面许可时，不进入上述验证码/会话联调。任一核心状态无法稳定读取、必须绕过控制、或者官方拒绝代理登录/保存会话，维持 `NO-GO`，回退到客户手动粘贴邀请码与人工审核。

## 当前建议

当前不要开始私有接口端到端联调、完整生产开发或真实付款。先向 SiliconFlow 申请书面合作/接口授权；若无法取得，则将 MVP 改为客户手动粘贴邀请码、抢单人跳转官方页完成、客户在官方“我的邀请记录”人工核验，本站不收 SiliconFlow 验证码、不保存其会话，也不自动读取认证状态。这一回退版可以开发任务管理和人工结算，但无法自动、无客户负担地证明首次有效认证。即使后续取得授权，仍需设置字段漂移熔断、人工审核降级和一键停止新抢单的开关。
